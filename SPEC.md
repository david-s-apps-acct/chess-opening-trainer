# Chess Opening Trainer — Spec

## Overview

A browser-based chess practice program. It pulls the user's studies from lichess.org and quizzes the user on the correct next moves.

**Writing guideline (the user's, 26 October 2026):** users are assumed to be intelligent and experienced at chess. Everything on screen uses as few words as possible: brief labels, messages and hover hints rather than long explanations. Longer explanations belong on the Help page.

## Lichess access

- Covers all of the user's studies, including private ones.
- Authenticates with a personal API token that the user generates once in Lichess account settings (Preferences → API access tokens).
- The token needs the `study:read` scope so private studies can be read.
- The user enters the token once; the browser remembers it (localStorage) so it isn't asked for again.
- The app should offer a way to clear or replace the stored token (on the Options page).
- A new token is checked with Lichess before it is saved; if Lichess rejects it, the app says so and doesn't store it.

### Fetching studies

- **Studies are updated from Lichess each time the app opens** (the user's decision, 2 November 2026; until then only when the user pressed an "Update studies" button on the Options page, which is gone). See Automatic study updates. The first visit (nothing cached yet) fetches automatically once the token is entered, then offers Restore backup or Start before anything downloads (see The welcome screen).
- **Automatic study updates** (the user's decision, 2 November 2026, replacing the Update studies button; the user asked for it to be documented):
  - **When:** each time the app opens, online, connected to Lichess and with the user's own studies (not the sample ones), the app first shows the studies it already has, then fetches them again in the background (one export request, as Update studies did). Reloading the page updates them at any time.
  - **Unchanged:** only the time they were fetched changes (the Options page's "Fetched 15 studies on …").
  - **Changed:** the new studies replace the stored ones, as Update studies did: stats for moves no longer in the studies are dropped, the tries' points are worked out again, the page on view is drawn again, and statistics for new positions download.
  - **During practice:** if a practice session is running when the update arrives, the new studies wait and replace the old ones when the session ends (End practice), so practice isn't interrupted; if the app is closed first, the next opening updates them again.
  - **Quietly:** nothing is shown while it happens. Offline, or if Lichess can't be reached, it's skipped. An expired Lichess connection shows "Lichess connection expired. Connect again on the Options page." in the Options page's Lichess studies card.
  - The downloads of missing statistics start after the update (or when it's skipped).
  - **Where it's described:** the Options page's Lichess studies heading on hover ("Your studies are updated from Lichess each time the app opens (reload the page to update them now); your stats are kept. Move and masters statistics then download in the background."), and Help's Options section.
  - *Claude's choices, accepted by the user:* the wording above; changes are recognised by comparing the fetched studies with the stored ones (names, chapters and their PGN); the update is skipped when the browser reports being offline.
- Fetched studies are cached in the browser between visits. Use IndexedDB rather than localStorage, since a full export of many studies can exceed localStorage's ~5 MB limit.

## Selecting what to practice

The user chooses the practice set at any of these levels:

- **Individual chapters:** one or more specific chapters, possibly from different studies.
- **A whole study:** all chapters in one study.
- **A set of studies:** all chapters in several chosen studies.
- **Everything:** all chapters in all of the user's studies.

**Layout:** a checkbox list of the user's studies, each expandable to show its chapters with their own checkboxes.

- Studies are listed alphabetically; chapters keep their order within the study.
- **Opening name:** hovering over a chapter's name on the Studies page shows the opening from the chapter's Lichess PGN tags, e.g. "Italian Game: Classical Variation, Greco Gambit, Traditional Line (C54)": the `Opening` tag, then the `ECO` code in brackets. If only one of the tags is there, just that is shown; with neither, there's no hover text. It's shown in the app's own small pop-up (like the comment bubbles), which appears after about 0.7 seconds (the user's decision in the UI clean-up, so it doesn't cover the moves that open when the name is clicked; before that all the app's pop-ups appeared immediately, and the delay was 0.15 seconds, then 1 second, before that), instead of the browser's standard tooltip, whose delay can't be set. (The tag describes the chapter as a whole, from its main line; variations deeper in the chapter may be other named openings.)
- Each study row shows its name, then in grey its number of chapters, e.g. "Ruy Lopez · 2 chapters".
- Each chapter row shows its name and side circle, then in grey its **number of lines**, e.g. "Main line Chigorin ● · 5 lines" ("1 line" when there's one; a chapter with no testable lines shows no count). (The alternative moves used to follow, e.g. "· 2 alternative moves", with an explanation on hover; the user removed them, 6 October 2026. History: the counts were first on the study rows, as "4 chapters · 37 lines (+5 side variations)", then "· 5 alternative moves"; the user moved the line and alternative-move counts to the chapter rows.)
- Each study row's **chapter count** (e.g. "· 7 chapters") underlines on hover and shows or hides the study's chapters when clicked, the same as the study's name (the user's request, 6 October 2026).
- An **alternative move** (called a "side variation" until the user asked for clearer wording) is another move for the user in the study, at one of the user's turns on a practiced line (e.g. 3. Bb5 where the main move is 3. Bc4). Each counts once, however many moves follow it; alternative moves inside other alternative moves aren't counted. They aren't practiced as lines (see Branches) and aren't included in the line count. The counts appear on chapter rows; study rows show only the number of chapters. The line count doesn't change with "Main line only"; the count at the top of the right-hand panel shows how many selected lines will actually be practiced.

- Ticking a study ticks all its chapters; unticking it unticks them all.
- If only some of a study's chapters are ticked, the study's checkbox shows a partial (indeterminate) state.
- Chapter rows are indented one tab (32px) to the right of their study's checkbox, on all screen sizes, so chapters clearly sit under their study. A chapter's two triangles sit under its study's ▸ and checkbox, so the chapter's checkbox stays one tab in.
- **A chapter's move tree:** each chapter row has its own ▸ button (like a study's) that opens the chapter's moves underneath it, indented one more step; ▾ closes them (hover: "Show moves" / "Hide moves"). Only the ▸ opens them; clicking the chapter's name still ticks or unticks it. A chapter with no testable lines (e.g. an unsupported variant) has no ▸ button, just a space.
  - The moves are shown as a tree, the way Lichess shows a study: the **main line** always shows, flowing along in Lichess style ("1. e4 e5 2. Nf3 Nc6 3. Bc4"). After a move that has alternatives, a small **+** button opens those variations underneath, each on its own indented row (with a thin line down the left), each in the same style and with its own + buttons; **−** closes them. The main line then continues on a new row ("3… Bc5 4. c3"). Variations start closed. Every move and variation in the study is included.
  - **All-variations triangle:** each chapter row has a second small triangle, just right of the moves triangle and left of the checkbox (so there are two side by side). It points right (▸) when the variations are closed and down (▾) when they're all open. ▸ opens every variation in the chapter at once, including variations inalternative moves and alternative moves, and also opens the chapter's moves if they're closed; ▾ closes all the variations (the moves stay shown). The individual + / − buttons keep working afterwards, and they don't change the triangle: after ▸, it stays pointing down even when single variations are closed with their −, until the triangle itself is clicked (which closes all of them). Likewise, opening every variation one by one doesn't turn it down. (At first it pointed down only while every variation was open; the user asked for it to change only when clicked.) Hover: "Show all variations" / "Hide all variations". A chapter without variations has an empty space there, so checkboxes stay lined up. (This replaced a "+ all / − all" button above the main line, at the user's request.)
  - All moves are in the standard text color (see Progress tracking for the highlighting of weak moves, and Comments and glyphs for glyph colors); move numbers are grey; **alternative moves at the user's moves** (never practiced), and everything after them, are in italics with no score. Move glyphs and comment bubbles appear as in the practice move list, following the annotations icon. Comment bubbles are the same soft blue as everywhere.
  - Every move has the small hover board (see Colored moves and the hover board). A side-variation move shows the position after it, like an opponent's move, labeled "Alternative move, not tested", with the move drawn as a white arrow, or an amber arrow if the study marks it ?, ?? or ?!.
  - Open chapters and open variations stay open while the user moves around the app (like open studies), until the page is closed or reloaded.
  - History: this replaced a list of the chapter's lines (in study order, each with its colored moves, weakest score, evaluation and a "main line" label, with "Show all N lines" for chapters over 100 lines), at the user's request, together with the switch to per-position scores.
- An "All" checkbox at the top selects or clears everything.
- Each chapter and each study shows the user's average move accuracy next to it, shown as just the percentage, e.g. "82%", with a one-sentence explanation in the hover pop-up (the same immediate pop-up as the opening names): "Average move accuracy over the last 10 attempts" (first "Accuracy over the last 10 attempts", the user's wording after grading moved to points; "Average move" was added with the move/line accuracy terms). (It said "82% right", then "82% correct moves", until the user asked for just the number with a hover explanation; the pop-up then said "How often you play your moves here correctly: the average over the 5 moves you've tried, each over its last 10 tries.") The figure is the average score of the moves the user has tried across all its lines (see Progress tracking), highlighted with the same ranges as the moves (see Progress tracking). Moves not tried yet don't count toward the average; if nothing has been tried, nothing is shown. A chapter with no testable lines (e.g. an unsupported variant, or no moves for the user) still says "no lines to test". (It used to show a miss rate per line.)

**End of each line in the move tree** (removed 3 November 2026, the user's decision: on the Review page the tree shows where each line ends, and untested moves are in italics, so the underline added nothing): the **last move of each line** you practice is **underlined** in a chapter's move tree, so each line's end is easy to see (the user's request). *Claude's choice, accepted by the user:* the ends of untested alternative moves' variations (in italics) aren't underlined, since they aren't lines you practice.

**Clicking names:** clicking a study's name shows or hides its chapters (the same as its ▸), and clicking a chapter's name shows or hides its moves as a tree, starting with the main line (the same as its ▸); Enter or Space on a focused name does the same. Clicking a chapter's **number of lines** (e.g. "3 lines") shows or hides **all its variations** (showing them also shows the moves, and hiding them leaves the main line showing). Each chapter has **one ▸**, for its moves (the user's decision in the UI clean-up; a second ▸ used to open all its variations, the same as the number of lines); a chapter without variations has a plain count. (The user's request.) Selecting or deselecting a study or chapter is done only with its checkbox (clicking a name used to tick its checkbox; the user changed this). *Claude's choices, accepted by the user:* a name underlines on hover to show it can be clicked; a chapter with no lines to test (e.g. an unsupported variant) has a plain name; the chapter name's opening pop-up stays.

**Layout:** the list of studies and chapters is on the left, with the "All" checkbox at the top of the list, lined up with the studies' checkboxes. The selection controls are in a panel on the right: the count of chapters and lines, e.g. "2 chapters selected" (without the number of lines, the user's request; it used to add e.g. "· 4 lines"). (It also held a "Start practice" button and the "Opponent's moves" and "Where lines start" radio buttons; the user removed them: the Studies page only selects studies and chapters, and practice starts from the Lines and Positions pages.) (The "Show annotations" and "Show chapter names" checkboxes used to follow; they were replaced by icons on the practice page, which were later removed too.) Longer descriptions of these options show as hover tooltips. The panel stays in view while the list scrolls. On narrower screens (under about 800px) the panel moves above the list.

**Hidden studies:** a study the user no longer wants to see can be hidden; individual chapters can't (the user's choice).
- **The top eye:** a small eye icon in the presets bar, just right of the presets' pencil (the user moved it there as a more natural place; it was at the right-hand end of the "All" row). With a line through it (the normal state), hidden studies aren't in the list and study rows have no eye. Without the line, hidden studies appear in the list in grey (dimmed) and every study row gets its own eye. Hover: "Show hidden studies" / "Stop showing hidden studies". It's always clickable, even when nothing is hidden (it's also the way to hide studies), and isn't remembered: the list always opens with the line through it. There's no count of hidden studies.
- **Each study's eye** (only while the top eye is open), immediately to the right of the study name, before "· 2 chapters": a plain eye for a visible study (click to hide it; no message is shown, the user's decision, 6 October 2026; it used to say "Hid "Ruy Lopez". It won't be practiced."), an eye with a line through it for a hidden one (click to unhide it). So hiding a study is: open the top eye, click the study's eye, close the top eye.
- If every study is hidden (with the top eye closed), the list says "All your studies are hidden. Click the eye at the top to see them."
- **Excluded from practice:** hiding a study unticks all its chapters, and while it's hidden its checkboxes are disabled, so it's never practiced. "All" ticks only visible studies. Choosing a saved selection skips chapters in hidden studies and says how many it skipped. Practice itself also ignores any chapter in a hidden study.
- Its stats are kept, so unhiding brings everything back as it was (its chapters stay unticked until ticked again). The automatic Lichess downloads still fetch data for hidden studies.
- Hidden studies are remembered between visits, included in backups, and survive Update studies (a study deleted on Lichess is dropped from the hidden list).
- History: first built with a "Show hidden (2)" text button and an eye that appeared at the end of a study row on hover; the user changed it to the top eye and per-study eyes after the name.

### Move popularity (Lichess database)

- **Automatic, in the background:** move statistics download by themselves, with no button: whenever the app opens (after the studies have been updated), so a download that was interrupted resumes, and after studies are fetched or replaced. Only positions without statistics are fetched; if nothing is missing, nothing is said. Update studies itself still finishes straight away. (History: at first they downloaded automatically after every refresh; then only with a "Refresh move frequency" button, later "Download move frequencies", in its own Options page box; the user then asked for automatic downloads again, without the button.) Move statistics download first, then Masters statistics.
- **Every position reached in the studies** is downloaded: every move and variation, including alternative moves' variations and each line's final position (earlier only positions where a move is played on the practiced lines were; the rest were added for the position count on the hover boards). For each, it's how often each move is played in the Lichess games database: all rated Lichess games, all ratings and time controls, not the Masters database. It uses Lichess's Opening Explorer (`explorer.lichess.org/lichess`), which requires the stored Lichess token (with no token, move statistics wait until one is saved; saving a token restarts the downloads).
- **What's saved for each position:** the Opening Explorer's answer **exactly as Lichess sends it** (`white`, `draws`, `black` for the games reaching the position; `moves`, a list with each move's `uci`, `san`, `averageRating` (the average rating of the players who made the move), `white`, `draws`, `black` and anything else Lichess includes; `topGames` and `recentGames`, empty because none are requested; and `opening` with its `eco` and `name`, or none for an unnamed position). The only thing dropped is moves beyond the **10 most played** (Lichess lists them most played first), except that any other move the studies have at that position (the user's main moves, opponent replies and alternative moves) is kept, so a rarer repertoire move still has its count and doesn't show 0%. Moves are matched ignoring + and #. Two fields are added: `v` (the format, 3) and `at` (when it was downloaded, used when merging a backup). A position no game reaches, found without asking Lichess, is saved in the same shape with zero games and `skipped`. The request still asks for up to 100 moves so the studies' rarer moves can be found. Nothing new is displayed yet; the position count and live ECO code (future improvements) will use it. (An interim version saved a reshaped copy, with moves keyed by name and `averageRating` renamed; the user asked for Lichess's own shape.)
- Positions saved before this (totals only) were treated as missing, so the next download fetched them all again with the details; until then their percentages still showed.
- Only positions that haven't been downloaded before are fetched; each position is fetched once even if it's in several lines. Results are saved in the browser (IndexedDB) and kept across visits.
- Requests are made one at a time, with no pause between them (there's no batch endpoint, so one request per position is the minimum). If Lichess answers "too many requests", the app waits a minute and carries on.
- **Most useful first:** positions in the selected chapters where the opponent has several replies come first (they drive "Prefer most common moves"), then the rest of the selected chapters, then everything else; within each group, shallower positions come before deeper ones.
- **Skipping positions nobody reaches:** if every known way into a position is a move that no Lichess game played (according to the statistics already downloaded for the position before it), the position is marked "no games" without a request. This is a close approximation: a different move order could occasionally reach such a position. (There used to be a finished message saying how many were skipped; it went with the Options page's fewer words, 26 October 2026.)
- **Progress** shows in the Options page's Lichess studies card as "Move statistics: 120 of 850 positions (downloading…)" (since 26 October 2026; there used to be a separate "Downloading move statistics: …" line and a finished message). Practice can continue while it runs; positions not downloaded yet have no percentages. A line under it appears only for problems: "Couldn't reach Lichess. The rest downloads next time.", "Lichess asked to slow down: waiting a minute…", and "Lichess rejected the token. Replace it below to continue." (after which the download continues). A running download skips positions whose statistics arrived meanwhile, e.g. from a restored backup (a fix of 26 October 2026: it used to fetch everything it had listed when it started), and suggests a backup only if it fetched something itself. Closing the page stops the download; it resumes the next time the app opens.
- **Download order** (the same whatever is ticked, across all studies): (1) branch points (positions where the opponent has several replies), then (2) the rest of the chapters' main lines, then (3) everything else; within each group by move number (move 1 first). (It used to put the ticked chapters first.) A deep branch point may be fetched before the positions leading to it, so the "no game reaches it" shortcut can't always apply and a few extra requests are made; accepted.
- **Masters statistics:** for the same positions, the app also downloads Lichess's **Masters** database (over-the-board games between players rated 2200+ FIDE, from 1952): `explorer.lichess.org/masters?fen=…&moves=100&topGames=0`, also with the Lichess token. The answer is saved **exactly as Lichess sends it with the full move list** (masters positions usually have only a handful of moves), but **without the top master games** (none are requested, so `topGames` comes back empty), plus `v` (1) and `at`. It's stored separately from the Lichess games data (IndexedDB key `masters`), downloads automatically in the background after the Lichess games statistics (same order, same "no game reaches it" shortcut: "skipped because no master game reaches them"), has its own lines in the Lichess studies card ("Masters statistics: 850 of 860 positions"), is included in backups and merged on restore (the newer copy of each position wins), and gets its own backup suggestion when complete (only once every position really has them: a fix of 26 October 2026, since a download whose requests all failed used to suggest a backup too). About 2 MB for ~1,800 positions. **Nothing displays it yet**; the user will decide how to use it.
- **Backup suggestion:** when a download finishes and every position has its statistics (not when nothing was missing, or when it stopped part-way), the **Backup card** (now on the Lichess page) suggests a backup (the user's decision, 2 November 2026; it used to be in the Lichess studies card): "Move statistics downloaded. Save a backup?" (or "Masters statistics downloaded. …") with **Save backup** and **Not now** buttons.
- The Move frequency section of the Options page always shows how many positions have statistics, e.g. "Move statistics: 850 of 860 positions downloaded." It adds "(downloading now…)" while a download is running, updating as it goes, or "The rest downloads automatically after Update studies, or when you next open the app." when some are missing and nothing is downloading.
- The percentages appear only on the small hover boards (in the move tree, and in the practice move list once a line is over), never during the quiz. (The summary used to list them all, e.g. "In Lichess games: 1. e4 45% · 1… e5 48% · 2. Nf3 62%"; the user removed that list, since the hover boards show the same numbers.) A move's share is the number of games with that move divided by all games in that position. Shares below 1% show as "<1%"; a move not played in any game shows "0%"; a position with no games shows "no games"; a position not downloaded yet shows "–". Single positions have no summary, so they don't show percentages.
- The Help page explains the automatic downloads (under Getting started) and that hovering over a move in the summary shows its percentage (under Practicing).

### Both sides and your choices (5 November 2026; not built, still being thought through)

- **Why (the user's reasons):** a study may give you two choices at one of your moves (e.g. an aggressive A against a weaker player, a solid B against a stronger one), and a study may be meant for both sides (e.g. the user's Ruy Lopez, played as White and as Black).

- **Reverse sides goes** (the user's decision). Playing only the other side of a chapter (e.g. only Black from a White study) is no longer possible; accepted by the user.
- **Main lines only** accepts only the main line, for either side (the user's decision): your study's main move at your turns, the opponent's main move at theirs.
- **Main lines only off:** any of your study's moves at a position is accepted, and the line follows it (Claude's reading of the user's decision, to confirm). Moves the study marks ?, ?? or ?! stay errors (Claude's detail, accepted by the user).
- **Accuracy is per position within a chapter** (the user's decision: it better matches how chess is played): the position where it's your move has one record, whichever of your study's moves you play; the same position in another chapter keeps its own (no mixing across chapters).
- **Many more lines; line accuracy works as now** (the user's point). *Claude's detail:* a line's key gets the side added, since the same line played as White and as Black ends on the same move.
- **Spaced repetition for the alternative lines needs more thought** (the user's decision). *Claude's suggestions, for the user to consider:* (1) a line through one of your other choices starts just after that choice (the app plays the moves up to and including it, e.g. "from 6. d3"), so habit doesn't keep those lines untried; (2) a line's or position's Frequency counts only the opponent's moves (the product of their shares; your own moves count as 100%), so a rarely played choice of yours doesn't sink its lines.
- **Right or wrong, with no partial penalties** (the user's decisions, 5 November 2026):
  - **Correct:** your study's main move, or one of its unmarked alternatives (with Main lines only off; with it ticked, only the main move).
  - **Incorrect:** a move the study marks ?, ?? or ?!, any move not in the study, or the hint (and Show correct move).
  - **Two move accuracy figures per position, from the same attempts** (the user's decision, 5 November 2026, replacing "with Main lines only, an alternative is just taken back, not incorrect"; open to reconsidering later). The history already stores every move tried, so there's no second record, only two readings:
    - **Any study move** (Main lines only off): right if the first move tried is any of your study's unmarked moves.
    - **Main line** (Main lines only ticked): right if the first move tried is the main move. In Main lines only mode an alternative is therefore wrong (taken back like any error). Attempts made with Main lines only off whose first move was one of your alternatives are left out of this figure, since you were free to choose it (Claude's detail, accepted by the user).

### Punish moves (4 November 2026; not built, its use still to decide)

- **The user's definition, in two steps** (to save downloads):
  1. **Suspect moves:** opponent moves, from any position in a study where it's the opponent's move, that are played **10% of the time or more** in the position (at the chosen Lichess ratings and time controls; the user's decision, 5 November 2026, since a rarely played move isn't worth testing; it replaced "among the top 10"), in at least 50 games, and whose result for the side playing them is 10 points or more below the position's (e.g. Black scores 50% from the position but 38% after the move). These come from the move statistics already downloaded. The move needn't be in the study.
  2. **Of those, the ones that drop the opponent's winning chances by 10 points or more** by Lichess's cloud evaluation (Lichess's own "mistake" threshold, so blunders count too). Only suspect moves (and the positions they're played from) get cloud evaluations. A move with no cloud evaluation is treated as fine (the user's reasoning: a position nobody has analysed is very unlikely to occur).
  - 10 points is the user's choice "for now" (Claude suggested 5, to also catch mistakes that aren't often punished at the user's level). The 50 games was Claude's suggestion, accepted by the user. *Claude's detail, for the user to accept or reject:* the 50 games stays alongside the 10%, since in a rarely reached position 10% can be a handful of games.
- *Claude's details, for the user to accept or reject:*
  - Winning chances are Lichess's formula, on a 0–100 scale: from 0.00, 10 points is about −1.1.
  - The cloud evaluations download in the background after the masters statistics, throttled like them, and are kept in IndexedDB and in backups.
- **Separate from the study's own glyphs** (the user's decision): a study's ?, ?? and ?! keep their meaning and behaviour (`isMistake`), and the engine's verdict is a separate thing.
- **Names (the user's decision, provisional: "we can refine the name later"):** the first group are **suspect moves**, the sub-group **punish moves** (the opponent's moves worth learning to punish). "Mistake" stays reserved for the study's ?, ?? and ?! (`isMistake`).
- **Use (the user's decision):** somewhere in the Practice section, to be decided later. The opponent plays a punish move and you give a **refutation** (the user's provisional name).
- **Judging a refutation (the user's decisions):** completely separate from the studies (the simplest): the engine decides even where the study answers the punish move. A refutation is correct if it's within **5 points of winning chances** of the engine's best move (Lichess's inaccuracy threshold), so several moves can be correct.
  - *Claude's details, for the user to accept or reject:* the engine's moves come from the same cloud evaluation that confirms the punish move (the position after it), asked for Lichess's top 5 moves (`multiPv=5`), so no extra downloads; a move not among them counts as incorrect; after an incorrect refutation the app shows the engine's best, e.g. "Engine: ♘xe5 (+1.8)".
  - *"Completely separate" (Claude's reading, confirmed by the user):* refutations don't count towards move accuracy, line accuracy or spaced repetition, and an incorrect one isn't called an "error" (which means a move that isn't your study's); they'd have their own record.

## Progress tracking

- Results are recorded **per move, at each position in a chapter**, and kept between visits (stored in the browser, like the token and selection).
- A **line** is one path through a chapter from the start to the end of a variation, following the main line at every user move and any variation at opponent moves. It is identified by its study, chapter, and move sequence.
- **One record per position:** each of the user's moves has one record per point in the chapter's move tree, identified by the chapter plus the moves leading to and including it. Every line that passes through that point shares the record, so getting 3. Bc4 right in one line counts for every line that continues from it. The same board position in a **different chapter**, or reached by a **different move order**, keeps its own record (the user may play differently in different contexts). This also applies to the times recorded (when each position was last tried, and line times). The user confirmed that history is **not** to be merged across chapters.
- History: at first, records were kept per line (the same move in two lines, even with the same moves before it, was recorded separately). The user asked to drop line scoring and keep only the scoring of moves at a position, which also gives the move tree one score per move. Existing per-line records were merged into the position records when the app was next opened: each line's results for a move joined that position's record, keeping the most recent 10 (older backups are converted the same way when restored).
- For each of the user's moves, the app keeps its **last 10 attempts**. Older attempts drop off. Each attempt saves:
  - **what the user did, in order:** every move tried (wrong moves, alternative moves marked or not, and the correct move at the end if it was played) and the moments the Hint and Show correct move buttons were pressed, e.g. `["d4", "Bc4", "hint", "show", "e4"]`; a correct first try is just `["e4"]`; an attempt cut short by Skip or End practice has no correct move at the end;
  - its **points**, 0–10 (see Grading an attempt).
- **Grading an attempt:** each attempt starts at **10 points**; finding the correct move on the first try keeps all 10. Every step before the correct move costs points, each time it happens (repeats cost again):
  - an **unmarked alternative move** from the study: **−2** by default (the **Alternative move** penalty);
  - a **masters move**: **−2** by default (the **Masters move** penalty). A masters move is one **within the top 3** master moves in that position (moves played equally often share a rank, so a tie at 3 counts) **and** played in **10% or more** of master games there (from the Masters statistics). E.g. if only 2 moves reach 10%, only those 2 count; a 3rd move at 6% doesn't. (Top 3 was fixed on 3 November 2026, the user's decision: the "Masters moves" drop-down, Top 1 to Top 5 with a default of Top 5, was removed, since the 10% rule does most of the work. The penalty's hover text now says what a masters move is: "A top-3 master move, played 10% of the time or more, not in your study.") A move that is both an unmarked alternative and a masters move costs the alternative's penalty, once. (It was "more than 10%" with no top-N limit until the user made it configurable.)
  - an **alternative marked ?!, ? or ??**: **−5** by default (the **Error** penalty; the study's marking wins over a masters move);
  - **any other wrong move**: **−5** by default (the **Error** penalty). (Errors were −10 until the user lowered them to −5; the hint stayed at −10.)
  - the **Hint**: **−10** by default (the **Hint** penalty); **Show correct move** costs the same again, so with the default the score is already 0.
  - **The penalties are set on the Options page**, in a card titled **"Error penalties"** (first "Error penalties reducing move accuracy"; shortened with the Options page's fewer words, 26 October 2026): one drop-down each for Alternative move, Masters move, Error (which covers marked alternatives too) and Hint (which covers Show correct move), each **0%, 10% … 100%** of an attempt's score (1 point = 10%), defaults 20%, 20%, 50%, 100%; and, a little apart at the end of the card, **"Masters moves"**, Top 1 … Top 5, default Top 5 (it was between Masters move and Error until the UI clean-up, then under its own small heading with the label "What counts as a masters move"). Each name explains itself on hover (it used to have a short grey explanation after it). Changing any of them **re-scores all saved attempts straight away**, so the highlighting, the Studies page percentages and the Positions page reflect it at once. They're remembered and included in backups. *Claude's choices, accepted by the user:* the card is the first on the Options page; a line in progress keeps the points already worked out for the moves played so far in it.
    - **Built 3 November 2026 (the user's decision): fixed penalties, no Error penalties card.** The penalties can no longer be changed: an alternative 20%, a masters move 20%, any other error 50%, the hint (and Show correct move) 100%, as the defaults are now. The Error penalties card on the Options page goes, with its sliders and Reset, and so does the setting (`settings.errorPenalties`; a saved one, or one in a backup, is ignored). *Claude's details, accepted by the user:* the penalties stay as fixed rules in the code (one list, as now) and Help still says what each kind of error costs; the hover on Your accuracy and the "Errors: …" labels are unchanged; the Options page is left with Spaced repetition focus (whether to simplify Options further is a separate decision).

  - The floor is **0**. So an attempt scores 10, 8, 6 or 4 when the only slips were reasonable moves, 5 after one real mistake, 0 after two, and 0 after the hint. If a position's masters statistics haven't downloaded yet, no move there counts as a master move.

Its points are worked out from that, with the current rules and data (e.g. masters statistics downloaded since, or alternatives added in Update studies), when it's recorded, when the app opens, after restoring a backup, and when a penalty changes. - The Help page explains both (Practice › Spaced repetition › How the priority is worked out, "Last tested"; before 26 October 2026, Your statistics, "When lines and positions were last practiced"): a line counts only when played all the way through, from move 1 to the end; a position counts whenever it's attempted, so it can be more recent than any line through it (the user asked for this to be in the Help).
- A move's **move accuracy** (in the code, its score) is the **weighted** average points of its last 10 attempts (or however many there are), as a percentage of 10. Recent attempts count more: the most recent is weighted 100%, the one before 90%, then 80% … down to 10% for the 10th most recent; the score is Σ(weight × points) ÷ Σ(weights). E.g. attempts of 0, 8, 10, 10 (oldest to newest): (10×1.0 + 10×0.9 + 8×0.8 + 0×0.7) ÷ 3.4 ≈ 7.5, i.e. 75% (a plain average would be 70%). The hover board's "Average 7.5 of 10" is this weighted average. (It was a plain average until the user asked for recent attempts to count more.) Percentages are rounded down, so a score just under a boundary keeps the lower color. The score drives everything as before: the highlighting, the Studies page percentages, and the weights for "Prefer lines I miss" and Test single positions (a move's wrong rate being 1 − score).
- History: at first each attempt was just right (first try, no hint) or wrong, saved as 1 or as the list of wrong moves played, and unmarked alternatives weren't counted. The user asked for this points system. Existing results were converted when the app next opened: right became `[correct move]` with 10 points; wrong became the saved wrong moves (or `["hint"]` for an attempt that was only a hint or Show correct move), scored with the new rules (a hint used after a wrong move wasn't recorded then, so those may score a little high until they age out).
- **Highlighting** (a chapter's move tree and the Studies page scores): the move text stays in the normal color, and only moves that need work are highlighted, with **one violet background for anything below 100%** (the user's decision, 6 October 2026: simpler, and the shades no longer helped; 100% and untried are plain). The same violet marks studies, chapters, lines, positions and the practice move list's moves that lost points. (It used to come in three strengths: faint for 90–99%, medium for 70–89%, strong for 69% or less.) *Claude's choice, accepted by the user:* the violet is between the old medium and strong tints. ## Terms: move accuracy, line accuracy, errors and position reached

- The app uses two terms, consistently everywhere the user reads them (the user's standing rule):
  - **Move accuracy:** how well one of the user's moves is known, as a percentage. For one attempt it's the attempt's points × 10, e.g. "**80% move accuracy**" on the practice hover board (it used to say "80% accuracy this time"). Over time it's the weighted average of the move's last 10 attempts (see Progress tracking), e.g. "**75% move accuracy (last 4 tries)**" on the move tree's hover board (it used to say "Average 7.5 of 10 (last 4 tries)").
  - **Line accuracy:** the average move accuracy of the user's moves in one completed line, e.g. "**92% line accuracy**" under "Line complete." (it used to say "overall accuracy").
  - **Error** and **mistake** are different (the user's standing rule): an **error** is any move the user plays that isn't the one in their study (their preferred line), and the hint; errors are what cost move accuracy (the hover boards' "Errors: …" rows, "No errors." after a clean line, the Options page's "Error penalties reducing move accuracy"). **Mistake** is reserved for moves a study marks as a mistake (?), blunder (??) or dubious (?!) (the user decided to count ?! as a mistake, consistently through the app; the Help page explains both terms under Your statistics), e.g. "♗b5? is one of your alternative moves, marked as a mistake" and "Prefer opponent's mistakes". (The move tree's hover board used to say "Wrong: Bc4 ×2, d3", now "Errors: ♗c4 ×2, d3"; the Options card was "Mistake penalties".)
  - **Position reached:** how many times a position was reached in rated Lichess games (from the move statistics), shown with the same short counts everywhere (see Naming positions): "**Position reached 23k times**" on the hover boards (the position after the move) and the column "**Position reached (times)**" on the Positions page (the position where it's the user's move; the column used to be called "Lichess games").
- Where they appear: the practice and move-tree hover boards, the end of a line, the positions table (title "Frequent positions with low move accuracy", column "Move accuracy"), the Studies page's percentages (hover text "Average move accuracy over the last 10 attempts"; it used to say "Accuracy over the last 10 attempts"), the Options page's error penalties text and the Help page. The Help page and the rest of this spec say "move accuracy" where they used to say a move's "score". *Claude's choices, accepted by the user:* the Studies page hover text adds "Average" because a study's or chapter's percentage averages several moves; the move tree's hover board shows a whole percentage, rounded down like the Studies page.

## Naming positions

- **Counts of games** (the positions table's Position reached (times) column and the hover board's "Position reached … times") are shortened the same way everywhere: up to 999 as they are, then thousands ("23k"), millions with one decimal ("1.4M"), and billions with one decimal ("1.8bn", the user's request, instead of e.g. "1846.5M"). Both use exactly the same rule (the hover board used to show "<1k" below a thousand; the user asked for one rule everywhere), so e.g. "Position reached 950 times". With no games at all, the hover board says "Position never reached".
- **Everywhere the app names a specific position**, it uses the convention of chess books and sites (the user's standing rule): the **deepest opening name that applies** (Lichess's name for the position or the last named position before it, "Opening: Variation, Sub-variation"), then **the moves played since that named position**, at most the last 3 full moves with "…" before them when there are more, e.g. "Italian Game: Giuoco Piano, 4. c3 ♘f6 5. d4 exd4", and always at least the last move played, e.g. "King's Pawn Game, 1… e5". No "your move N": whose move it is follows from the last move listed. "Starting position" before any move.
- Where it's used: the positions table's Position column; the Practice panel's line under the chapter name for a single position, e.g. "Weak and frequent positions: Italian Game: Giuoco Piano, 4. c3 ♘f6" (it used to say "Single position, move 5").
- Places that name a single **move** rather than a position (the hover boards' top line "5. c3", the Hint's "The move is 5. c3", comment pop-ups, wrong-move messages) keep the move label.
- Any new place that names a position must use this convention.

## Technology

- **Version control:** the project folder is a local git repository (no GitHub or upload), set up at the user's request; each agreed change can be committed as a snapshot and undone by going back to an earlier one. The first commit recorded the app, spec, project notes and the natural-language archive.

- **Delivery:** a single HTML file, `index.html` (called `trainer.html` until 26 October 2026, renamed at the user's request so the GitHub Pages address needs no file name), opened directly from disk (`file://`) or from GitHub Pages. No server, no build step.
- **Lichess API:** called directly from the page; the Lichess API allows cross-origin browser requests.
- **Libraries:** chessops and chessground (JS and CSS) are loaded from the jsDelivr CDN via ES module imports. The app needs internet to reach Lichess anyway, so this adds no new requirement online.
- **Keeping the data** (the user's decision, 28 October 2026): once there are studies (fetched, sample, or on opening), the app asks the browser to keep its data ("persistent storage"), so it isn't cleared when space runs low or, in Safari, after 7 days without a visit. Browsers decide for themselves (Firefox may ask the user once); it isn't a guarantee, so backups still matter.
- **Browsers** (28 October 2026): the app needs a browser from 2022 or later (Safari 15.4+, current Chrome, Edge and Firefox); the user isn't concerned about older ones. Phones and tablets are still to be tried on real devices (the hover hints need a mouse).
- **Offline** (discussed 26 October 2026): once the studies are fetched, everything except Lichess (Update studies, the statistics downloads, connecting) can work offline. The online version keeps its files with a service worker (see Publishing on GitHub), so it works offline reliably. The copy opened from disk relies on the browser's ordinary cache (jsDelivr marks the libraries cacheable for a year), which isn't guaranteed: a cleared cache or a private window means it can't start offline; the user chose to leave it that way.
- **PGN parsing:** use [chessops](https://github.com/niklasf/chessops), the library Lichess itself uses. Its `chessops/pgn` module parses study PGN into a move tree that keeps all variations, and its move logic validates the user's moves.
- **Font:** Noto Sans from jsDelivr (`@fontsource/noto-sans`), plus Noto Sans Symbols 2 (`@fontsource/noto-sans-symbols-2`) for the chess piece symbols; only the subset containing the symbols is downloaded.
- **Move statistics:** Lichess Opening Explorer API (`explorer.lichess.org/lichess`), called from the page with the Lichess token.
- **Sounds:** Lichess's SFX move and capture sounds, served by jsDelivr from the `lichess-org/lila` GitHub repository at a pinned commit.
- **Board UI:** use [chessground](https://github.com/lichess-org/chessground), Lichess's board library, which pairs with chessops. The user makes moves by dragging or clicking pieces on it. It uses Lichess's default look (brown board, cburnett pieces); no other board or piece styles are offered.

## Possible future improvements

Ideas agreed or mentioned along the way that haven't been built yet:

- **The first-run choice in the Move statistics card** (discussed 3 November 2026; kept for future consideration, the user's decision, not to build now). The user's idea: the Backup card has only Save backup, and the Move statistics card shows Restore backup and Download statistics only while the statistics aren't downloaded. Claude's concerns: Restore backup brings back history, settings, presets and ticks too, so it should stay available after the statistics are complete; and "not downloaded" recurs whenever a study is added (its new positions have none), so the buttons would keep coming back. - **Ideas from research into what 1400+ and 1800+ players need** (30 September 2026; suggested by Claude after the user asked; not yet discussed in detail, so each needs the user's decisions before building). In Claude's suggested order of value:
  1. **Your Lichess games compared with your repertoire** (both levels; highest value): fetch the user's recent Lichess games with the stored token and, for each, find where the user left the repertoire (a forgotten move: those come up first in practice) and where the opponent left it (a gap in the studies, listed by how often it actually happened).
  2. **Spaced repetition, "due today"** (both levels; built in its own form: the spaced repetition behind Practice, see Spaced repetition): using the per-position last-tried times already recorded, give each move a review interval that grows when it's answered well and resets when it isn't (Chessable's intervals run roughly 4 hours, 1 day, 3 days, 1 week, 2 weeks, 1 month, 3 months, 6 months), and a "Due moves" practice mode that tests only what's about to be forgotten.
  3. **Move statistics for the user's rating band** (both levels, especially 1400+; built 3 November 2026, see The Lichess page): download the Lichess move statistics filtered by rating (e.g. 1400–2000) and time control instead of all ratings, so "Prefer most common moves", the Positions page and the hover board's ranks and shares reflect what the user's own opponents play.
  4. **Gap finder** (mainly 1800+): for each position in the studies where it's the opponent's move, list the replies played at least about 5% of the time (at the user's level) that the study doesn't answer, plus a coverage percentage per chapter; perhaps a second table on the Positions page.
  5. **Punishing common mistakes** (mainly 1400+): find opponent replies that are popular at the user's level but score badly for the side playing them (from the win/draw/loss figures Lichess sends), and flag those the study doesn't answer.
  6. **Model games for each line** (both levels): at the end of a line, show two or three master games that reached that position (the Masters database's top games, not requested today), with links to play through them on Lichess, to learn the plans behind the moves.
  7. **Transposition awareness** (mainly 1800+): when the position reached also appears in another chapter or by another move order, say so (e.g. "Same position as Italian, after 4. c3"); information only, the histories stay separate.
  8. **Speed of recall** (both levels, for blitz and rapid): record how long each answer takes and treat slow correct answers as weaker.
  - Claude's recommendation: start with 1 and 2, and do 3 early since it's a small change that improves several existing features.

## Ideas for a separate app

Not part of this app; recorded so they aren't lost.

- **AI game reviewer that explains moves** (30 September 2026): an app to evaluate a whole game, combining a chess engine (Stockfish or Lichess's cloud evaluations) with an AI (Claude) that explains *why* a position is better for one side and why a move is good or bad, in human terms (pawn structure, king safety, piece activity, plans), rather than only giving numbers and engine lines.
  - How it would work (Claude's outline): the engine supplies the facts (evaluation, best moves, the refutation of a mistake); code works out the concrete board features (material, pawn structure, king safety, open files, loose pieces); the AI turns these into an explanation; and the engine checks each claim (e.g. that a stated threat really works), discarding explanations that don't hold up. Where an evaluation rests on deep tactics with no human-sized reason, it should say so instead of inventing one, and small differences between good moves aren't worth explaining.
  - Why separate (the user's decision): explanations matter most at a game's turning points, mostly in the middlegame, rather than in prepared openings, whose ideas the study comments already cover; a game review has a natural shape (find the turning points, explain only those), which also keeps the number and cost of AI questions low; and it keeps this app free of an API key, an engine download and per-question costs.
  - A possible link: finding where a game left the repertoire is close to this app's future idea of comparing your Lichess games with your repertoire, so the two could share that step.
